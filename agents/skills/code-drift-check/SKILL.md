# Code Drift Check

意味が決まった後に実装だけが動き、コメント・名前・テスト・周辺の要素が追随していない箇所を拾う。
意味契約の確定や照合は `code-meaning-check`、バグ探しは code-review の担当で、ここでは扱わない。
仕様の正しさ、テスト設計の質、性能、lint・フォーマットも対象外。

## lint や diff レビューで足りない理由

- 未使用検出の多くは非公開の要素しか報告しない（例: Go の staticcheck `unused`）。公開された死蔵コードは出ない
- コメント・テスト名・doc の主張は静的解析の対象外
- stale なコメントは触っていない行にある。だから残ったのであり、diff だけを読んでも見つからない

## 2つの使い方

|  | 自分の変更の後 | 頼まれたレビュー |
|---|---|---|
| 対象 | このタスクで入れた変更。未コミットなら `git diff HEAD`、コミット済みならタスク開始時点との差分。加えて触ったファイル全体 | ブランチ全体（`git diff $BASE...HEAD`） |
| 見つけたもの | 自分の取り残しなので、その場で直す | 直さずに報告する |
| 出力 | 直したものを一言ずつ。指摘ゼロなら検査した範囲を一言 | 下の「報告の形式」 |

自分の変更でも、直すのに意味の判断が要るもの（コメントとコードのどちらが正しいか分からない等）は、直さずにユーザーへ聞く。

## 手順

### 0. 足場

このスキルはプロジェクト固有の値を持たないので、最初に調べる。
比較の基点、生成物の目印（ファイル先頭の `Code generated` / `DO NOT EDIT` / `@generated`）、型チェックとテストのコマンド、doc コメントの記法。

- 作業ディレクトリを明示する。モノレポでは間違った側で実行してもエラーにならず、0件が返る
- 生成物は対象外。直す必要があればテンプレートやスキーマ側
- 頼まれたレビューでは、設計変更・不変条件の確立・方針転換を主張するコミットから見る。`refactor:` などの件名より、本文に書かれた背景や理由が手がかりになることが多い
- 後段の「消して型チェック」の比較用に、変更したサブツリーだけを1回型チェックしておく。フルビルドは遅い

### 1. コメントの主張

最も多く見つかるのがここ。**触ったファイルはコメントを通読する。** 変更行の周辺だけでは足りない。

- 「〜が使う」「〜だから」「〜のため」は検証できる主張。名指しされた利用者や理由を実際に確かめる
- 不変条件の主張を集めて並べる。1つずつ読むと矛盾に気づけない。
  同じ関数の中で「既存データが不変条件を破っている」と「不変条件により成立している」が、同じコミットで併記されていた例がある

  ```
  grep -rn '不変条件\|常に\|必ず\|だけ\|唯一\|一致しない\|混在\|invariant\|always\|never\|only' <触ったディレクトリ>
  ```

- コメントやテスト名が名指しする識別子が実在するか照合する。記法はプロジェクトごとに違うので、既存ファイルから決める（行頭の `[識別子]`、バッククォート、`@see` など）。
  照合した件数も出す。0件という結果と、入力が0件だったことを区別できないと検査にならない

  ```
  # 例: 行頭 [識別子] 形式の場合
  for n in $(grep -rhoE '^\[[A-Za-z][A-Za-z0-9_]*\]' <対象> | tr -d '[]' | sort -u); do
    grep -rq "<その言語の宣言パターン>${n}\b" <対象> || echo "実在しない: $n"
  done
  ```

- `TestXxx` の `Xxx` が実在しないなら、テスト本体が空洞化していないか見る。対象の呼び出しが消え、入力を同じ入力と比べるだけになっている形。
  無条件に通って誤った安心を与えるので、stale なコメントより害が大きい
- 方針転換は要素の削除を伴わないことがある。「X しない」と書いた後で X を始めると、コメントだけが残る。日付を比べる

  ```
  git log -S '<追加された要素の名前>' --oneline $BASE..HEAD
  git log -S '<コメントの一節>'        --oneline $BASE..HEAD   # 断片は一意になるまで長くする
  ```

コメントが書かれていること自体を品質のシグナルにしない。もっともらしい理由はいくらでも書けるし、自分が書いたコメントも例外ではない。

### 2. 参照されていない要素・到達しない分岐

関数だけでなく、型・定数・変数・代入形式も拾う。重大な指摘は、定数や変数の側から出ることが多い。

差分の追加行から宣言を抽出し、テストのエントリポイント（`Test*` / `spec` / `it(` 等）を除いて、参照をテストと非テストに分けて数える。

| 非テスト | テスト | 判定 |
|---|---|---|
| 0 | 0 | 死蔵の候補 |
| 0 | あり | 最も疑わしい。テストのためだけに生きている |
| 1以上 | — | 通常 |

**確定は「消して型チェック」で行う。** その前に、対象の言語で消して型チェックが何を証明しないかを確かめる。遅延評価の言語では未参照の要素を消しても通り、文字列やシェル変数を経由した参照は型チェックからは見えない。

多くの言語では通常のビルドがテストコードを型チェックしないので、2段で見る。テストが無いなら2段目は不要。

- テストを含まない型チェックが通る → 非テストからの参照は0
- テストを含む型チェックでだけ失敗する → テストからの参照がある

例: Go なら `go build ./<対象>/...`（テストを含まない）と `go vet ./<対象>/`（テストを含む）。確認したら必ず元に戻す。

誤判定は両方向に起きる。

- 同名のメンバが別の型にあると、テキスト検索では参照ありに見えて見逃す。呼び出し側の受け手の型を読む
- インターフェースを満たすためだけのメンバは、消しても型チェックが通るので、誤って死蔵と断定しやすい

参照0が出たら、まず動的な呼び出しを疑う。リフレクション・DI コンテナ・ルーティング表、フレームワークが規約で呼ぶメンバ、テストランナーが名前で拾うエントリポイント、生成コードの慣習など。
正常と判断するのは、それを呼ぶ実装箇所を1つ特定してからにする。

新しく足した分岐やエラーには、そこへ到達する入力を1つ書いてみる。書けないならテストも書けず、おそらく要らない。

差分が markdown や設定ファイル中心で宣言を抽出できないときは、代わりに、本文が名指しするファイルや識別子の実在と、付随するファイル（別ツール向けのメタデータや設定）が本文の変更に追随しているかを見る。

### 3. 定数があるのに生文字列

型付き定数や列挙があるのに、リテラルで比較・代入していないか。
同じファイルのテスト側は定数を使っているのに実装側はリテラル、という形が出やすい。

### 4. 命名

doc コメントを隠して名前だけを読み、中身を予想する。外れたら改名を検討する。

- 動詞に目的語がない（`normalize` は何を正規化するのか）
- 名乗っている分類軸と実際の処理がズレている（`getFooTableNames` が実は特定種別の除外）
- テスト名が対象の旧名のまま残っている
- 規約には沿っているが、規約自体が読み取れない

### 5. 2件以上見つかったら共通の根を疑う

複数の指摘が、設計を作り直したときの追随漏れ1件にまとまることがよくある。個別に直す前に、同じ変更から来ていないか確かめる。
原因が契約レベルのズレだと分かったら、`code-meaning-check` に回す。

## 報告の形式（頼まれたレビュー）

1. Findings — 重大度順。`file:line`、どの検査で見つかったか、由来（範囲内で入った／範囲より前からある）を付ける。触ったファイルを通読するので範囲より前からある問題も拾う。由来がないと、ブランチで入った退行と誤読される
2. 共通の根 — 2件以上あれば束ねられるか
3. 確認しきれなかったもの — 判断がつかなかった箇所と理由
4. 問題なしと判断したもの — 誤爆を防ぐため明示する

| 重大度 | 基準 | 動作影響 |
|---|---|---|
| 高(意味) | コメント／名前が、コード・実行環境・他の記述と矛盾していて、レビュアーがどちらが正しいかを聞かざるを得ない | 無いことが多い。修正は数行 |
| 高(動作) | 誤った結果を返す、または保証が抜けている | ある |
| 中 | 読めば分かるが、なぜ在るのか説明できない（死蔵、契約外の参照） | 無い |
| 低 | 慣習からの逸脱、既存パターンとの不揃い | 無い |

高(意味)と高(動作)は混ぜない。レビューのコストは同じでも、直すコストが桁違いだから。

指摘ゼロなら `No findings` と明言し、検査しきれていない範囲を添える。

## 検査を足したくなったら

見逃しが出ても、すぐには検査を足さない。項目を増やすほど当たり率が下がることは実測で確かめている。
先に `references/dropped-checks.md`（実測で0件だったために外した検査と、その理由）を読む。
