# Code Drift Check

**意味の確定は扱わない。** それは `code-meaning-check`（承認済み意味契約との照合）の役割。
このスキルは、**意味が決まった後に実装だけが動いて、周辺が追随していない**箇所を拾う。

## なぜ lint で足りないか

- **多くの未使用検出は、外部公開されていない要素しか報告しない。** 公開された死蔵コードは出ない
  （例: Go の staticcheck `unused` は未エクスポートのみ）
- コメント・テスト名・doc の主張は静的解析の対象外
- **stale なコメントは定義上、差分の外側にある。** 触っていないから残ったのであり、
  `git diff` だけを読む限り原理的に見つからない

## 収録している検査は実測で選別済み

fresh-context の別エージェントによる2回の独立実測で件数を記録し、**0件だった検査は落とした**。
落としたものは末尾に記録してある。**見逃しが出たら検査を足すのではなく、まず落とした一覧を見直すこと。**
検査項目を増やすほど当たり率が下がるのは実測済み。

## 手順

### 0. 足場を作る

**このスキルはプロジェクト固有の値を持たない。最初に調べる。**

| 調べるもの | 調べ方 |
|---|---|
| 比較の基点 | `git symbolic-ref refs/remotes/origin/HEAD`、または PR のベースブランチ |
| 生成物の除外パターン | 変更ファイルの先頭を見て `Code generated` / `DO NOT EDIT` / `@generated` を探す |
| 型チェック・テストのコマンド | `Makefile`、CI 設定、`AGENTS.md` / `CLAUDE.md` を読む |
| 対象言語のコメント記法・doc 記法 | 既存ファイルを1つ読む |

```
BASE=$(git merge-base <ベース> HEAD)
git diff --stat $BASE...HEAD -- <対象拡張子> <生成物の除外>
git log --oneline $BASE..HEAD
```

**作業ディレクトリを明示する。** モノレポではリポジトリルートとモジュールディレクトリで
相対パスの意味が変わり、**間違った側で実行するとエラーも出ず0件で返る**。実測で1回踏んだ。

生成物は対象外。直す必要があればテンプレート・スキーマ側。

**優先順位。** コミットメッセージが**設計変更・不変条件の確立・方針転換**を主張しているものを先に見る。
`refactor:` だけを見るのは誤り。実測では `refactor:` の13行コミットが最も綺麗で0件、
実際の道標は `docs:` コミットのメッセージだった。

**ベースラインの型チェックを1回通す。** 後段の「消してビルド」の比較対象になる。
**フルビルドではなく変更サブツリーに絞る**（実測ではフルが cold で5分超、サブツリーは数秒）。

### 1. コメントの主張 ← 最大の当たり所

実測2回で、重大な指摘のほとんどがここから出た。

**差分が触ったファイルは、変更行の周辺だけでなくコメントを通読する。**
stale なコメントは触っていない行にあるので、差分だけ見ても出てこない。

**「〜が使う」「〜だから」「〜のため」は検証可能な主張。** 名指しされた利用者・理由を実際に確認する。

**不変条件の主張を集めて相互に突き合わせる。**

```
grep -rn '不変条件\|常に\|必ず\|一致しない\|混在\|invariant\|always\|never' <触ったディレクトリ>
```

個別に読むと矛盾に気づけない。並べると気づける。実測では、同一関数内で27行離れて
「既存データが不変条件を破っている」と「不変条件により成立している」が併記されていた。
しかも**同一コミットで両方入っていた**（stale ではなく、書いた時点で矛盾）。

**コメント・テスト名が名指しする識別子の実在を照合する。** doc の記法はプロジェクトごとに違うので、
既存ファイルを見てパターンを決める（行頭の `[識別子]`、バッククォート、`@see` など）。

```
# 例: 行頭 [識別子] 形式の場合
for n in $(grep -rhoE '^\[[A-Za-z][A-Za-z0-9_]*\]' <対象> | tr -d '[]' | sort -u); do
  grep -rq "<その言語の宣言パターン>${n}\b" <対象> || echo "実在しない: $n"
done
```

**検査した件数も出すこと。0件と入力0件を区別できないと検査として成立しない。** 実測で踏んだ。

**`TestXxx` の `Xxx` が実在しないなら、テスト本体が空洞化していることがある。**
対象の呼び出しが消え、入力を同じ入力と比べるトートロジーだけが残る形。
**無条件に通るので気づけず、stale コメントより悪質**（誤った安心を与える）。

**方針転換は要素の削除を伴わないこともある。** 「Xしない」と書いた後で X を始めた場合、
コメントは残る。日付を比べる。

```
git log -S '<追加された要素の名前>' --oneline $BASE..HEAD
git log -S '<コメントの一節>'        --oneline $BASE..HEAD   # 断片は一意になるまで長くする
```

> **コメントが書かれていること自体を品質のシグナルにしない。**
> もっともらしい理由は生成できる。自分が書いたコメントにも当てはまる。

### 2. 参照されていない要素・到達しない分岐

**関数だけでは足りない。型・定数・変数・代入形式も拾う。**
実測では重大な指摘がすべて定数・変数・コメント側にあり、関数限定の抽出から1件も出なかった。

差分の追加行から宣言を抽出し、テストのエントリポイント（`Test*` / `spec` / `it(` 等）を除く。

**参照はテストと非テストを分けて数える。**

| 非テスト | テスト | 判定 |
|---|---|---|
| 0 | 0 | 死蔵の候補 |
| 0 | あり | **最も疑わしい。** テストのためだけに生きている |
| 1以上 | — | 通常 |

**確定は「消して型チェック」。ただし2段構えが必要。**

多くの言語で、通常のビルドコマンドは**テストコードを型チェックしない**。それだけでは上の表を測れない。

- テストを含まない型チェック → 成功なら「非テスト参照0」の証明
- **テストを含む型チェック** → そこでのみ失敗すれば「テスト参照あり」の証明

例: Go なら `go build ./<対象>/...`（テストを含まない）と `go vet ./<対象>/`（テストを含む）。
他の言語でも「テストまで型チェックする経路」を先に特定する。確認後は必ず元に戻す。

**限界が両方向にある。**

- 同名のメンバが別の型にあると、テキスト検索は参照ありと誤判定して**見逃す**。
  参照数が0にならなくても、呼び出し側の受け手の型を読む
- インターフェース充足のためだけに存在するメンバは、消しても型チェックが通り、
  **誤って死蔵と断定する**

**参照0が出たら、まず動的解決を疑う。** 静的に呼ばれていなくても正常なものがある。

- 名前や文字列からの動的ディスパッチ（リフレクション、DIコンテナ、ルーティング表）
- フレームワークが規約で呼ぶメンバ（ライフサイクル、ポリシー、スキーマ定義）
- テストランナーが名前で拾うエントリポイント
- 生成コードや慣習で全ファイルに同型のものが並ぶ場合

**それぞれ実装箇所を1つ特定してから「正常」と判断する。** 推測で除外しない。

**新規の分岐・エラーには、到達する入力を1つ書く。** 書けないならテストも書けない。書けないなら要らない。

### 3. 定数があるのに生文字列

型付き定数・列挙が存在するのにリテラルで比較・代入していないか。実測2回とも1件出た。

**同じファイルのテスト側が定数を使っているのに実装側がリテラル**、という形が出やすい。

### 4. 命名

**doc コメントを隠して名前だけ読み、中身を予想する。** 外れたら改名。

- 動詞に目的語が無い（`normalize` は何を正規化するのか）
- **名乗っている分類軸と実際の処理がズレている**（`getFooTableNames` が実は特定種別の除外）
- **テスト名が対象の旧名のまま残っている**
- 規約に沿っているが規約自体が読み取れない（正しくてもレビューで質問される）

### 5. 2件以上引っかかったら共通の根を疑う

実測では、重大な4件すべてが「設計を作り直したときの追随漏れ」1件に束ねられた。
個別に直す前に、同じ変更由来でないか確認する。

**ただしこれは個別に検出できて初めて働く。** 束ねる材料が無ければ機能しない。
契約レベルのズレは `code-meaning-check` の担当で、このスキルでは拾えない。

## 出力フォーマット

1. **Findings** — 重大度順。`file:line` 必須。どの検査で引っかかったかを付ける
2. **共通の根** — 2件以上あれば束ねられるか
3. **確認しきれなかったもの** — 判断がつかなかった箇所と理由
4. **問題なしと判断したもの** — 誤爆防止のため明示する

| 重大度 | 基準 | 動作影響 |
|---|---|---|
| 高(意味) | コードとコメント／名前が矛盾。レビュアーが「どちらが正しいのか」を聞かざるを得ない | 無い場合が多い。修正は数行 |
| 高(動作) | 実際に誤った結果を返す／保証が抜けている | ある |
| 中 | 読めば分かるが、なぜ在るのか説明できない（死蔵、契約外の参照） | 無い |
| 低 | 慣習からの逸脱、既存パターンと不揃い | 無い |

**「高(意味)」と「高(動作)」を混ぜない。** レビューコストは同じでも修正コストが桁違いになる。

指摘ゼロなら `No findings` と明言し、検査しきれていない範囲を添える。

## 落とした検査（実測値つき・復活させる前に読むこと）

見逃しが出たときに安易に項目を足さないための記録。

| 検査 | 実測 | 落とした理由 |
|---|---|---|
| 消えた要素名を diff から抽出しコメント照合 | 25抽出→6照合→**0件** | ノイズ19件。net diff はブランチ内で追加後に削除された要素を拾えない。識別子の実在照合（手順1）で代替 |
| 外部識別子の値の重複（`uniq -d`） | 11→1件、10→**0件** | 重複自体は正常（文脈をまたいだ同義の名前）。判断が全部人手に残る |
| まとめる／分ける判断（抽象の妥当性3軸） | **0件**、2回とも | 対象が1-of-1 のとき反証不能で、必ず「妥当」に着地する。抽象を足した箇所が複数ある差分でのみ有効 |
| 到達入力を1つ書く（独立項目として） | **0件** | 手順2に1行として統合した |

## 検査しないもの

- **意味の確定** → `code-meaning-check`
- 仕様の正しさ
- テスト設計の質（言語別のテストレビュー用スキルがあればそちら）
- 性能
- lint / フォーマット（プロジェクトの lint コマンドで足りる）
