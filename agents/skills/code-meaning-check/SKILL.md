# Code Meaning Check

記入テンプレートと記入例は `references/meaning-contract.md` にある。

**確定した契約はプロジェクト側の設計ドキュメント（チケット、ADR、`docs/` など）に記録する。**
このスキル配下へ承認記録を蓄積しない。記録先が決まっていなければ、それを先に決める。

## なぜ必要か

意味はコードから発見するものではなく、**コードへ与える入力**である。

人間は意味を選ばないと次の判断へ進めない。不明点が停止信号になる。**AIは停止しない。**
周辺コードから局所的にもっともらしい前提を補完し、構文的に正しくスタイルも整い、
why コメントとテストまで揃った「考え抜かれた設計に見える誤り」を作る。詰まらなかった痕跡すら残らない。

型のない入れ物（`map`、`dict`、`JSON`、動的に組むレコード）がこの補完を助ける。
別の契約に属する正当な識別子を持ってきても、定義は見つかり、コンパイラも通る。

## 実装前 — 契約を確定させる

**公開契約・ID・派生モデルを変える場合、承認済みの意味契約なしに編集を開始しない。**

1. 対象の**公開語彙、値の所有者、導出関係、禁止する状態・遷移**を列挙する
2. **「したがって何を読まないか・受け付けないか」まで書く。** 導出できる値を入力として受け取らない
3. 人間 owner の承認を得る。承認記録を特定できなければ、ここで停止して承認を求める

肯定の定義（この値は何か）だけでは実装は止まらない。**否定（何を受け付けないか）が契約の効く部分**である。

## 実装後 — 契約と差分を照合する

1. 承認済みの意味契約があることを確認する。対象値が誰の契約に属するかと、人間 owner による承認記録を
   特定できなければ、実装レビューを停止して契約の提示または承認を求める

2. 差分を意味契約の各項目と照合する。公開語彙、値の所有者、導出関係、禁止状態・遷移がすべて一致するか

3. 契約外キー、導出できる値の二重保持、別文脈のエラー語彙がないか確認する
   - **その値はこのレコード／型の契約に属するか。** 「識別子が実在するか」ではない。
     別の契約に属する値は、定義元を引いても見つかるので素通りする
   - 導出できる値を入力として受け取っていないか。**兆候は「等しく設定する処理」と
     「等しいことを検証する処理」の同居**。設定するなら検証は不要、検証するなら設定は不要
   - 境界で利用側の語彙へ翻訳できているか。**計算（数値・真偽の算出）は文脈非依存で再利用でき、
     表現（エラー名・メッセージ・列名・ID）は文脈依存で、そのままでは再利用できない**

4. コメントとテストが契約を反証していないか確認する。契約外の入力・状態を正当化または固定している場合は、
   **個別の症状ではなく原因となる契約違反へまとめて報告する**

## 報告の単位

**症状ごとに並べない。違反した契約項目ごとにまとめる。**

1つの意味論のズレは、複数箇所の小さな症状として現れる。個別に並べると「小さな指摘がN件」に見え、
1つの設計判断の欠落だと分からない。レビュアーから見ると「意味の分からない処理がN箇所ある」になる。

## 扱わないもの

- 実装への追随漏れ（stale コメント、死蔵コード、空洞化したテスト、命名のズレ）→ `code-drift-check`
- 仕様の正しさ、性能、lint
