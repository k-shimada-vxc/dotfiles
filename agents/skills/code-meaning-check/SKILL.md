# Code Meaning Check

意味はコードから見つけるものではなく、コードへ与える入力である。

人間は意味が決まらないと次へ進めず、不明点がそのまま停止信号になる。AI は止まらない。
周辺コードからもっともらしい前提を補い、構文もスタイルも整い、why コメントとテストまで揃った
「考え抜かれた設計に見える誤り」を作る。迷った痕跡も残らない。
型のない入れ物（`map`、`dict`、JSON、動的に組むレコード）はこの補完を助ける。
別の契約に属する正当な識別子を持ってきても、定義は見つかり、コンパイラも通る。

このスキルは、意味を決める場面で止まり、人間に決めてもらうためにある。
実装に周辺が追随していないかの確認は `code-drift-check` の担当。仕様の正しさ、性能、lint は扱わない。

## 1. 対象かどうかを判定する

対象になるのは、次のどれかの意味を新しく決める、または変える変更。

- 外部から見える契約: API、DB スキーマ、ID、イベント、ファイル形式など
- 派生モデル: 複数の実体を結合・変換した型やビュー
- 金額、権限（認可）、データの意味

外部から見える振る舞いが変わらない変更（非公開の型、内部のリファクタ、既存の契約に沿った実装の追加）は対象外。
「対象外: 理由」を一言述べて作業を続ける。迷ったら対象として扱う。

## 2. 実装前: 契約を決めて承認を取る

1. 対象の公開語彙、値の所有者、導出関係、禁止する状態・遷移を列挙する。テンプレートと記入例は `references/meaning-contract.md` にある
2. 「したがって何を読まないか・受け付けないか」まで書く。導出できる値を入力として受け取らない。
   肯定の定義（この値は何か）だけでは実装は止まらない。**否定（何を受け付けないか）が、契約の効く部分である**
3. 契約の表をユーザーに示して承認を求め、承認があるまで編集を始めない。周辺コードから導けそうに見えても、AI が決めて先へ進まない
4. ユーザーが明示的に承認したら進めてよい。確定した契約はプロジェクトの設計ドキュメント（チケット、ADR、`docs/` など）に残す。
   残す場所が決まっていなければ聞く。このスキルの配下には記録しない

## 3. 実装後: 契約と差分を照合する

1. 照合の基準になる承認済みの契約を特定する。見つからなければ照合を止め、契約の提示か承認を求める
2. 差分を契約の各項目と照合する。公開語彙、値の所有者、導出関係、禁止する状態・遷移がすべて一致するか
3. 契約外のキー、導出できる値の二重保持、別の文脈のエラー語彙がないか確かめる
   - 見るのは「その値がこのレコード／型の契約に属するか」で、「識別子が実在するか」ではない。
     別の契約に属する値は、定義元を引いても見つかるので素通りしやすい
   - 導出できる値を入力として受け取っていないか。兆候は「等しく設定する処理」と「等しいことを検証する処理」の同居。
     設定するなら検証は要らず、検証するなら設定は要らない
   - 境界で利用側の語彙へ翻訳できているか。計算（数値・真偽の算出）は文脈に依存せず再利用できるが、
     表現（エラー名・メッセージ・列名・ID）は文脈に依存するので、そのままでは再利用できない
4. コメントとテストが契約に反していないか確かめる。契約外の入力や状態を正当化・固定しているものは、
   個別の症状ではなく、原因になった契約違反にまとめて報告する

## 報告の単位

違反した契約項目ごとにまとめ、症状ごとに並べない。

1つの意味のズレは、複数箇所の小さな症状として現れる。個別に並べると「小さな指摘が N 件」に見え、
1つの設計判断が欠けていることが分からない。レビュアーからは「意味の分からない処理が N 箇所ある」ように見える。
