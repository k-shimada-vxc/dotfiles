# Go Test Quality Review

このスキルは **lint実行ではなく、テストコード読解レビュー** に特化する。

## 目的

- テストが仕様価値の高い振る舞いを検証しているかを判断する
- 過剰fixture・過剰分割・実装詳細依存を減らす
- テーブル駆動とアサーション設計を改善する
- 不要なヘルパー抽象化を抑え、読みやすさを保つ

## レビュー手順

1. 対象を特定する（ユーザー指定ファイル、または差分の `*_test.go`）。
2. まず `AGENTS.md` 等のプロジェクト方針を確認する。
3. `references/test-review-checklist.md` の観点でレビューする。
4. 指摘は **重大度順** に列挙する（`file:line` 必須）。
5. 最後に「最小変更での改善案」を提示する。

## 重要ルール

- `lint/testコマンド` は既定で実行しない（ユーザーが求めたときのみ）。
- 「直すべき設計上の問題」と「好み」を分けて報告する。
- 指摘ゼロなら明確に `No findings` と伝え、残留リスクだけ添える。

## ヘルパー方針（強調）

- 原則: テスト専用ヘルパーは作らない。まずテスト内で完結させる。
- 例外: 同じ Arrange が3回以上繰り返され、抽象化後も意図が明瞭な場合のみ許可。
- 不採用基準: ヘルパーを展開しないと仕様意図が読めない場合。
- 優先順: helper化より先に、fixture縮小とテーブル駆動統合を検討する。

## 出力フォーマット

1. Findings（重大度順）
2. Open Questions / Assumptions
3. Suggested Refactor Plan（小さく段階的）

## 呼び出し例

- 「$go-test-quality-check でこの `generator_test.go` の設計レビューをして」
- 「$go-test-quality-check で fixture 過多かどうか見て」
