# Test Review Checklist (Go)

## 0. 一般プラクティス

- 実装詳細ではなく公開契約・振る舞いを検証しているか
- 1テスト1意図になっているか
- テスト名が「条件_操作_期待結果」を表せているか
- Arrange / Act / Assert が読める構造か
- テストが決定的（時刻・乱数・外部I/O依存を抑制）か

## 1. 仕様価値（最優先）

- private helper の内部実装を直接固定していないか
- リファクタで壊れにくいテストか
- 境界値・異常系が仕様上必要な範囲で押さえられているか

## 2. fixture規律

- 大きなfixtureを惰性的に置いていないか
- fixture内容のうち、実際にアサートしていない値が多すぎないか
- 可能なら最小入力へ圧縮できるか
- 実ファイル参照の方が契約追従しやすいなら、インラインfixtureより優先する

## 3. テーブル駆動の適用

- 入力差分だけの検証を個別テストで重複していないか
- 正常/異常のバリエーションは table-driven でまとまるか
- テストケース名から期待挙動が読めるか

## 4. ヘルパー最小化（重要）

- 原則としてテスト専用ヘルパーを増やしていないか
- 同じArrangeの3回以上重複など、導入理由が明確か
- ヘルパー化で意図が隠れていないか
- helper化より先に fixture縮小・テーブル駆動統合を検討したか

## 5. 本質的でないテストの削減

- 単純getter/単純変換など、壊れても価値の低いテストを増やしていないか
- 既に上位の契約テストでカバーされる観点を重複していないか

## 6. アサーション品質

- 失敗時に原因が分かるメッセージ・粒度か
- `require`（前提）と `assert`（検証）を適切に分離しているか
- 1テストに複数責務を詰め込みすぎていないか

## 7. 保守性

- Arrange の重複が多すぎないか
- テスト名・subtest名が仕様を表しているか
- 将来の仕様追加時にケース追加しやすい構造か

## レビュー出力時の原則

- 指摘には必ず `file:line` を付ける
- 「必須修正」と「改善提案」を区別する
- 変更提案は最小差分で出す
