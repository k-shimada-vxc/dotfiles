# Subagent Code Review

このスキルは、レビュー依頼で独立した二重チェックを標準化する。

## 基本方針

- レビュー依頼を受けたら、最初に独立サブエージェントを1つ起動する。
- 差分が大きい、複数ファイルにまたがる、または論点が複数ある場合は、観点別に複数サブエージェントを並列起動する。
- サブエージェントには最小限の task-local context だけを渡す。自分の仮説や結論は渡さない。
- サブエージェントの結果は参考情報として扱い、必ずメインエージェント自身でも対象を確認する。
- 最終出力は findings 優先にし、重大度順に `file:line` 付きで列挙する。
- 指摘がなければ `No findings` を明示し、残留リスクや未確認点だけを添える。

## 実行手順

1. レビュー対象を特定する。差分、PR、ファイル、ディレクトリ、仕様のどれを見ればよいか確定する。
2. レビュー観点を決める。小さな差分なら1本で十分だが、大きい差分では観点別に分割する。
3. サブエージェント起動ツールが見えていない場合は、`tool_search` で multi-agent/subagent/workspace-agent 系を1回だけ探す。使えるツールがなければ、その制約を短く明示してメインエージェント単独のレビューへ進む。
4. 独立サブエージェントを1つ以上起動する。既存の文脈をそのまま渡さず、レビュー対象と依頼内容だけを渡す。
5. サブエージェントが走っている間に、メインエージェントはローカルで対象を確認し、前提や影響範囲を整理する。
6. サブエージェントの findings を受け取ったら、根拠を自分でも再確認する。
7. 自分の所見と統合し、重複を潰して最終レビューを作る。

## 観点別レビューの分割ルール

- デフォルトの観点候補は `正しさ/回帰`, `設計/保守性`, `テスト不足` とする。
- 差分に応じて `性能`, `セキュリティ`, `API互換性`, `データ整合性` を追加してよい。
- ファイル数が多いだけでなく、1つの変更に複数の失敗モードがあるときも観点分割を優先する。
- 同じ観点を複数エージェントへ重複依頼しない。分割は「ファイル単位」より「観点単位」を優先する。
- 小さな差分では無理に分割しない。観点が自然に1つへ収まるなら単独レビューでよい。
- 最終レビューでは「どの観点のサブエージェントが言ったか」ではなく、統合済み findings としてまとめる。

## サブエージェントへの依頼ルール

- 「レビューしてほしい」という依頼意図は渡してよいが、「このバグが怪しい」などの誘導は避ける。
- 可能なら raw artifact を渡す。例: 差分、対象パス、PR番号、仕様ファイル。
- 依頼文は短く保つ。例えば `この差分をコードレビューして。重大度順に findings を出して。` のように依頼する。
- 観点別に分けるときは、担当観点を明示する。例えば `この差分を正しさと回帰リスクの観点でレビューして。重大度順に findings を出して。` のように依頼する。
- サブエージェントの結論をそのまま採用せず、必ず一次ソースで裏を取る。

## 出力ルール

1. Findings
2. Open Questions / Assumptions
3. Change Summary

## 注意点

- 実装や修正よりレビューが主目的のときだけ使う。
- 小さな質問応答や単なる説明依頼では使わない。
- サブエージェント起動ツールが見つからない場合は、探索を繰り返さず通常のレビューを継続する。
- サブエージェントが失敗した場合は、その制約を短く明示して通常のレビューを継続する。
- 差分が大きい場合は、観点ごとにサブエージェントを増やすことを基本とする。ただし同じ観点の重複レビューは避ける。

## 呼び出し例

- `"$subagent-code-review でこの差分をレビューして"`
- `"$subagent-code-review で PR のリスクを見て"`
- `"$subagent-code-review でこのファイル群のコードレビューをして"`
